## 1. Исходная задача и требования

Проект — информационная система управления концертной деятельностью **одного музыкального исполнителя**.

Главный источник требований — [НИРС.pdf](../НИРС.pdf). Правила разработки находятся в [AGENTS.md](../AGENTS.md).

В начале в проекте были только эти два файла. Документ НИРС оказался доступен; его текст извлекался через pypdf. Для реализации схемы также были извлечены и визуально просмотрены все четыре части рисунка 14.

Принятые ограничения:

- Архитектура — модульный монолит.
- PostgreSQL — источник истины; mock-хранилища и SQLite для интеграционных проверок не применяются.
- Backend: FastAPI, SQLAlchemy 2, Alembic, Pydantic и Pydantic Settings.
- Денежные значения: Python Decimal и PostgreSQL NUMERIC(14,2).
- Схема БД изменяется только миграциями Alembic.
- Сохраняется модель из 12 таблиц НИРС.
- Связанные изменения выполняются транзакционно.
- Договоры и финансовая история не удаляются каскадно.
- Не реализуются продажа билетов, банковские платежи, релизы и графики этапов оплаты.
- Ошибки не заменяются фиктивными успешными ответами.
- Пароли, локальные настройки и данные БД не должны попадать в Git.
- Frontend пока ограничен структурой каталогов.

### Реализованные типы и ограничения

- Идентификаторы, внешние ключи и version — bigint.
- Суммы и бюджет — numeric(14,2).
- Время концертов и технические временные поля — timestamptz.
- Даты договоров и операций — date.
- Снимки аудита — jsonb.
- Поля обязательны, если в НИРС не указана возможность NULL.
- Восьми изменяемым предметным таблицам добавлены created_at, updated_at и version.
- account_role имеет составной первичный ключ.
- Внешние ключи используют ON DELETE RESTRICT.
- Уникальны login и employee_id учётной записи, code роли и категории, contract_id привлечения, ненулевой request_key.
- У договора уникальна комбинация counterparty_id, number, signed_on.
- Добавлены CHECK для положительных сумм, неотрицательного бюджета, корректного интервала концерта и перечисленных в документе кодов.
- POSTED требует request_key; VOID требует непустую причину.
- Добавлены индексы из раздела 1.10.

Команда запускается только вручную:

~~~powershell
python -m app.seed --confirm-test-data
~~~

### Защита

- APP_ENV по умолчанию — production.
- SEED_ENABLED по умолчанию — false.
- Требуется APP_ENV=development/test и SEED_ENABLED=true.
- Требуется явное подтверждение --confirm-test-data.
- Используется отдельный обязательный SEED_DATABASE_URL; DATABASE_URL приложения автоматически не подставляется.
- Имя целевой БД должно оканчиваться на _seed или _test.
- Автоматического запуска из FastAPI, Alembic или Compose нет.
- Данные записываются одной транзакцией.
- Advisory lock и блокировки таблиц защищают проверку/запись от конкуренции.
- Используются стабильные отрицательные ID и постоянные ключи набора.
- Не изменяются обычные последовательности ID.
- Неожиданные существующие данные или изменения набора приводят к отказу и откату вместо перезаписи.
- Не удаляются финансовые записи и не сбрасываются пароли.

Суффикс имени БД сам по себе не доказывает, что среда тестовая: нужна действительно отдельная непроизводственная база и роль.

Учётные записи используют независимые salted scrypt-хеши. Случайные пароли сразу отбрасываются: опубликованного общего тестового пароля нет.

## 7. Этап 4 — REST API справочников

Основание: FR030 и UC03.

Создали отдельные модули venue, counterparty, finance_category в repositories, schemas, services и routers. Общие механизмы вынесены в catalog.py соответствующих слоёв.

### Маршруты каждого справочника

| Метод | Путь |
| --- | --- |
| GET | /{module} |
| GET | /{module}/{id} |
| POST | /{module} |
| PATCH | /{module}/{id} |
| POST | /{module}/{id}/archive |

### Поведение

- Список с limit, offset, total и поиском q.
- По умолчанию в списке только активные записи; archived=true выбирает архивные.
- Архивная карточка остаётся доступной по ID.
- DELETE не реализован; архивирование сохраняет прежние связи.
- Контролируемые Pydantic-ответы вместо выдачи произвольных ORM-объектов.
- Проверка обязательных полей, длины, nullable-полей, вместимости и направлений.
- Для email добавлена зависимость email-validator.
- Неизвестные входные поля запрещены.
- PATCH и архивирование требуют текущую version.
- Изменения и аудит сохраняются одной транзакцией.
- Конфликт версий и дубликат возвращают 409; отсутствующая запись — 404; ошибки запроса — 422.
- Поиск параметризован; символы LIKE экранируются как литералы.

UC03 не задаёт точные ключи возможных дубликатов. В API явно зафиксирована политика нормализованных сочетаний:

- venue: name + city + address;
- counterparty: name + kind;
- finance_category: code.

Сравнение учитывает trim и Unicode casefold, включая архивные записи. Это политика сервиса, а не новые UNIQUE-ограничения схемы. Записи через API сериализуются по справочнику advisory lock; прямой SQL эту политику может обходить.

### Согласованная защита доступа

Поскольку вход и сеансы ещё не были реализованы, пользователь **явно согласовал HTTP Basic** как текущий способ защиты.

Проверяются реальные PostgreSQL-данные:

- Пароль в формате salted scrypt.
- Активность учётной записи и сотрудника.
- Наличие MANAGER.
- ADMIN без MANAGER не даёт доступ к предметным операциям.
- Недействительные/отсутствующие данные дают 401, недостаточная роль — 403.

Это не реализация полноценного сеансового входа/выхода по FR010. Вне localhost требуется HTTPS. Seed не выдаёт известного пароля для входа.

### Выявленные проблемы и результат

- Ответы создания и чтения имели разные смещения часового пояса; нормализовали время к UTC.
- PostgreSQL с локалью C не приводил кириллицу к нижнему регистру; поиск перевели на встроенную в PostgreSQL 18 collation pg_unicode_fast.
- Добавили тест «Москва»/«МОСКВА».
- Проверили архивирование справочников, на которые ссылаются реальные концерт, договор и финансовая операция.
- Проверили откат записи справочника при ошибке записи аудита.
- Итог: **92 теста прошли**, из них 18 API-тестов справочников.
- Ruff — без ошибок; alembic check — без расхождений.

Подробности: [catalog-api.md](catalog-api.md).

| PATCH | /concert/{id} | Исправление с expected version |
| POST | /concert/{id}/confirm | Подтверждение |
| POST | /concert/{id}/complete | Отметка проведения |
| POST | /concert/{id}/cancel | Отмена с причиной |

### Состояния

| Код | Значение |
| --- | --- |
| NEGOTIATING | На согласовании |
| CONFIRMED | Подтверждён |
| COMPLETED | Проведён |
| CANCELLED | Отменён |

Разрешены переходы:

- NEGOTIATING → CONFIRMED.
- NEGOTIATING → CANCELLED.
- CONFIRMED → COMPLETED.
- CONFIRMED → CANCELLED.

Прочие и повторные переходы отклоняются. Статус нельзя подменить через обычные POST/PATCH-поля.

### Бизнес-правила

- До подтверждения площадка и предлагаемый организатор могут отсутствовать.
- Ответственный обязателен по схеме и должен выбираться из активных менеджеров с активной учётной записью.
- Новые ссылки на архивные площадки/контрагентов запрещены; исторические ссылки сохраняются.
- ends_at строго позже starts_at; входное время должно содержать часовой пояс.
- Бюджет — неотрицательный Decimal с точностью NUMERIC(14,2); ответы форматируются до двух знаков.
- Подтверждение требует площадку и активного ответственного менеджера.
- Требуется ровно один настоящий ACTIVE MAIN_SHOW для этого концерта.
- Контрагент основного договора должен совпасть с организатором; направление основного договора — IN.
- Отсутствующий, черновой, закрытый, сервисный или относящийся к другому концерту договор не подходит.
- Отсутствие API договоров не заменяется успешной заглушкой: без подходящего договора подтверждение возвращает 409.
- Подтверждённые интервалы проверяются как [starts_at, ends_at): соседние границы допустимы.
- При редактировании подтверждённой карточки повторно проверяются договор и расписание.
- Все изменения требуют ожидаемую версию; устаревшая версия даёт 409.
- Отметка проведения допустима после окончания концерта.
- Для отмены обязательна непустая причина.
- Отмена не удаляет и не аннулирует договоры/операции, не создаёт возврат автоматически.

### Согласованное редактирование финальных состояний

Пользователь **явно разрешил исправления проведённых и отменённых карточек с проверкой версии и аудитом**.

Реализовано:

- PATCH сохраняет финальное состояние.
- Обновляет version и создаёт UPDATE-аудит с состоянием до/после.
- Не переписывает договоры или финансовые операции.
- Не сбрасывает причину отмены.
- Проведённый концерт сохраняет площадку/организатора и не переносится в будущее.
- Изменение организатора не должно противоречить имеющемуся ACTIVE MAIN_SHOW.
- Для обычного исправления проведённой карточки не требуется реактивация уже закрытого договора.

### Поиск

Параметры: starts_from, starts_before, city, status, limit, offset.

- Период фильтрует время начала: нижняя граница включается, верхняя — нет.
- Указанные границы должны возрастать и содержать часовой пояс.
- Период и город применяются одновременно через AND.
- Город ищется как регистронезависимая подстрока с поддержкой кириллицы.
- Без фильтра города в список попадают и концерты без площадки.
- Архивная площадка не препятствует историческому поиску.
- Сортировка: starts_at, затем id.

### Защита конкуренции и аудит

Все изменения концертов сначала получают общую для одного исполнителя транзакционную advisory-блокировку **810004**, затем блокируют существующий концерт через SELECT FOR UPDATE.

После ожидания строка перечитывается и проверяется version. Условия подтверждения читаются из настоящих таблиц под разделяемыми блокировками. Состояние, новая версия и аудит с настоящим actor_id фиксируются одной транзакцией; ошибка приводит к откату.

READ COMMITTED обеспечивает видимость результата победившего запроса после ожидания блокировки.

Будущие сервисы договоров и изменения ответственных должны соблюдать тот же порядок блокировок при изменении предпосылок подтверждения. Прямой SQL может обходить протокол приложения; новые триггеры и таблицы для этого не добавлялись.

### Проверки

Проверены успешные и ошибочные переходы, отсутствие настоящего договора, неверный организатор/направление, отсутствующие ссылки, архивные новые назначения, роль ответственного, бюджет/время, partial PATCH, версии, аудит, поиск и сохранение финансовых записей при отмене.

Для гонок использованы **два независимых PostgreSQL-подключения**, принудительно ожидавших одну реальную блокировку:

1. Подтверждение двух пересекающихся концертов.
2. Два подтверждения одного концерта.
3. Два переноса подтверждённых концертов в один интервал.
4. Перенос одновременно с подтверждением.

Во всех четырёх случаях один запрос успешен, второй получает 409; лишнего аудита и подтверждённых пересечений нет.
