# Финансовый журнал — FR080, FR090, UC07 и UC08

Маршруты доступны менеджеру через HTTP Basic.

| Метод | Путь | Действие |
| --- | --- | --- |
| POST | `/finance` | Зарегистрировать операцию в статусе `POSTED` |
| POST | `/finance/draft` | Создать черновик |
| PATCH | `/finance/{id}` | Изменить черновик |
| POST | `/finance/{id}/post` | Провести черновик |
| POST | `/finance/{id}/void` | Аннулировать учтённую запись |
| POST | `/finance/{id}/refund` | Зарегистрировать возврат по учтённой операции |
| GET | `/concert/{concert_id}/finance` | Получить операции по концерту |
| GET | `/concert/{concert_id}/finance/totals` | Получить поступления, расходы и результат по учтённым операциям |

Для регистрации передайте `concert_id`, `category_id`, `occurred_on` в формате YYYY-MM-DD, `direction` (`IN` или `OUT`), `amount`, `basis` и `request_key`. `contract_id` можно опустить. Дата операции не может быть позже текущей даты UTC. Сумма положительная с точностью до копеек и ограничениями `NUMERIC(14,2)`. В ответе сумма представлена строкой. Категория должна быть действующей, а направление операции должно соответствовать категории и указанному договору. Указанный договор должен относиться к тому же концерту.

Для черновика передаются те же поля без ключа. Укажите текущую `version` при изменении и проведении черновика. При проведении также нужен `request_key`. Учтённая запись хранит время проведения и автора создания. Пользователь, который проводит черновик, фиксируется в аудите. Номинал договора и сумма операции хранятся отдельно.

Ключ действует в пределах всей базы. Первый прямой запрос возвращает HTTP 201. Повтор с тем же автором, ключом и данными возвращает текущую запись с HTTP 200. Повтор проведения того же черновика по его ключу также возвращает существующую запись. Использование ключа для другой операции даёт HTTP 409. Блокировка ключа и ограничение уникальности PostgreSQL защищают от параллельной регистрации. Запись и аудит сохраняются одной транзакцией.

Для аннулирования передайте текущую `version` и непустую `reason`. Исходная запись получает статус `VOID`. Сумма, автор, время учёта и ключ сохраняются. Повторное аннулирование и аннулирование операции с учтёнными возвратами дают HTTP 409.

Для возврата передайте `occurred_on`, `amount`, `basis` и `request_key`. API создаёт отдельную запись `POSTED`, копирует концерт, договор и категорию, ставит противоположное направление и сохраняет ссылку `original_id`. Дата возврата должна быть между датой исходной операции и текущей датой UTC. Исходной может быть учтённая операция без `original_id`.

Доступная сумма равна исходной сумме за вычетом всех учтённых возвратов. При превышении API возвращает HTTP 409 и сообщает остаток. Расчёт под блокировкой исходной записи защищает от параллельных запросов с разными ключами. Если возврат аннулирован, его сумма освобождает соответствующую часть остатка. Повтор того же запроса этим менеджером возвращает существующую запись с HTTP 200. Конфликт ключа возвращает HTTP 409.

Итоги `income`, `expenses` и `net` рассчитываются по всем записям `POSTED` данного концерта. Поступления и расходы учитываются по направлению каждой записи, а `net` равен разнице. Записи `DRAFT` и `VOID` доступны в журнале и исключаются из итогов.

Список можно отфильтровать по `status` и разбить на страницы через `limit` (1–100, по умолчанию 20) и `offset` (по умолчанию 0). Без фильтра список включает все состояния. Сортировка по дате операции и идентификатору, от новых к старым.
