# Пользователи, сессии и аудит

## Вход и выход

1. Отправьте `POST /auth/login` с JSON-полями `login` и `password` и заголовком `X-Requested-With: ConcertCRM`. Ответ устанавливает cookie `concert_session` и возвращает роли и `csrf_token`.
2. Отправляйте cookie с запросами. Для `POST`, `PATCH`, `PUT` и `DELETE` передавайте `X-CSRF-Token` со значением той же сессии. После перезагрузки страницы токен можно снова получить через `GET /auth/me`.
3. Отправьте `POST /auth/logout` с cookie и CSRF-токеном. Сервер отзывает сессию и удаляет cookie.

Cookie содержит идентификатор учётной записи и случайный токен. PostgreSQL хранит хеш токена и срок действия. Вход обновляет токен текущей сессии. После блокировки отзываются все сессии учётной записи. Роли и активность проверяются при каждом запросе.

В `.env` задаются `SESSION_COOKIE_SECURE`, `SESSION_COOKIE_SAMESITE` (`lax` или `strict`) и `SESSION_TTL_SECONDS` (по умолчанию 28 800). Cookie всегда `HttpOnly`. Production требует HTTPS и `SESSION_COOKIE_SECURE=true`. Для локального HTTP на loopback можно задать `APP_ENV=development` и `SESSION_COOKIE_SECURE=false`.

## Учётные записи

На новой базе после `alembic upgrade head` первый администратор создаётся интерактивно из каталога backend:

```powershell
.\.venv\Scripts\python.exe -m app.bootstrap_admin --login YOUR_LOGIN --full-name "Your Name"
```

Команда запрашивает пароль без отображения. Она доступна при отсутствии активного администратора.

| Метод | Маршрут | Право и действие |
| --- | --- | --- |
| GET | `/admin/accounts` | ADMIN, список с `limit` и `offset` |
| POST | `/admin/accounts` | ADMIN, создать сотрудника, учётную запись и назначить роли |
| PUT | `/admin/accounts/{id}/roles` | ADMIN, изменить набор ролей |
| POST | `/admin/accounts/{id}/block` | ADMIN, заблокировать учётную запись и сотрудника |
| GET | `/audit/{object_type}/{object_id}` | История доступного объекта с пагинацией |

При создании передаются `full_name`, `position`, `login`, `password` и непустой список `roles`. `phone` и `email` необязательны. Для блокировки и изменения ролей нужны `version` и `reason`. При блокировке или снятии MANAGER с сотрудника с концертами в `NEGOTIATING` или `CONFIRMED` укажите `replacement_employee_id` другого активного менеджера. Передача назначений, блокировка и аудит выполняются в одной транзакции.

Система сохраняет доступ последнего активного администратора. Чтобы заблокировать его или снять роль ADMIN, сначала назначьте другого активного администратора. Пароли хешируются scrypt с индивидуальной солью. Хеши прежнего формата обновляются при успешном входе.

История сотрудников, учётных записей и ролей доступна ADMIN. История предметных объектов доступна MANAGER. Учётная запись с обеими ролями получает оба набора прав. История возвращает автора, время, действие, причину и снимки значений. Пароли, хеши и сессионные данные исключаются из снимков.

Предметные API используют сессионный доступ. Защищённые запросы без действующей сессии дают 401, без нужной роли или CSRF-токена — 403.
